# 聚水潭对接说明（零售出库未税总金额 · 月度）

## 1. 用到的接口

| 项 | 值 |
| --- | --- |
| 接口 | `/open/orders/out/simple/query`（销售出库查询，文档 docType=8 & docId=34） |
| 正式地址 | `https://openapi.jushuitan.com/open/orders/out/simple/query` |
| 测试地址 | `https://dev-api.jushuitan.com/open/orders/out/simple/query` |
| 请求方式 | `POST`，`application/x-www-form-urlencoded;charset=UTF-8` |

公共参数：`app_key`、`access_token`、`timestamp`(秒)、`charset=utf-8`、`version=2`、`biz`、`sign`。
业务参数全部放在 `biz`（JSON 字符串）里。

## 2. 关键取数条件

```json
{
  "status": "Confirmed",
  "date_type": 2,
  "modified_begin": "2026-08-01 00:00:00",
  "modified_end": "2026-08-31 23:59:59"
}
```

- `status=Confirmed` → **出库状态=已出库**（`WaitConfirm` 待出库 / `Delete` 作废 / `Cancelled` 取消）。
- `date_type=2` → 按**出库时间** `io_date` 过滤（`0` 是修改时间）。
- **时段间隔不能超过 7 天**，代码里按 7 天自动分段；`page_size` 最大 50，自动翻页并按 `io_id` 去重。
- 频率限制：并发 5 次/秒、100 次/分钟；超限返回 `code=199/200`，客户端自动退避重试（请求间隔 ≥ 0.62s）。

## 3. 未税总金额怎么来

接口**不返回税额字段**，返回的是含税口径金额。因此：

```
未税总金额 = Σ含税金额 / (1 + 税率)
```

- 取数口径 `amount_source`：`items.auto`（默认，推荐）/ `items.sale_amount` / `items.buyer_paid_amount`（买家实付）/ `items.seller_income_amount`（卖家实收）/ `order.pay_amount`（应付金额，**不要用**，见下）。
- 税率不填（0）时，未税金额 = 接口金额本身。
- 如果贵司口径是「接口金额即为未税」，把 `tax_rate` 设为 0 即可，无需改代码。

### 为什么默认口径是 `items.auto`（实测数据，2026-08）

淘系/拼多多平台规则屏蔽价格字段，导致**单一口径必然漏数**：

| 口径 | 含税金额 | 未税(13%) | 有金额的单数 |
| --- | ---: | ---: | ---: |
| `order.pay_amount`（应付金额） | 47,936.38 | 42,421.58 | 135 / 1947 |
| `items.sale_amount`（明细金额） | 47,936.38 | 42,421.58 | 135 / 1947 |
| `items.buyer_paid_amount`（买家实付） | 471,289.14 | 417,070.04 | 1532 / 1947 |
| `items.seller_income_amount`（卖家实收） | 471,884.87 | 417,597.23 | 1532 / 1947 |
| **`items.auto`（兜底合并）** | **519,225.52** | **459,491.61** | 1667 / 1947 |

规律：国内店铺（淘宝/天猫/1688）只有 `buyer_paid_amount`/`seller_income_amount` 有值，
跨境与自建站店铺（速卖通、独立站、国际站）只有 `sale_amount` 有值，两组互斥。
`items.auto` = 每个明细行内按 `sale_amount → buyer_paid_amount → seller_income_amount`
取第一个非零值，因此两类店铺都能覆盖。兜底顺序可用 `auto_fields` 调整，例如把卖家实收提前：

```bash
python scripts/seed_jushuitan_metric.py ... --auto-fields seller_income_amount,buyer_paid_amount,sale_amount
```

另有约 280 单（1947 − 1667）三个金额字段都为空，多为赠品/线下/无金额单据，需要业务侧确认是否计入。

## 5. 跑通顺序

```bash
cd backend

# 1) 用授权凭据直连自检（不写库）
python scripts/jushuitan_check.py --app-key <ak> --app-secret <as> --access-token <token> --period 2026-08 --tax-rate 13

# 2) 落库：连接 + 来源系统/对象 + 同步任务（每月 1 日 02:00）+ 指标定义
python scripts/seed_jushuitan_metric.py --app-key <ak> --app-secret <as> --access-token <token> --tax-rate 13

# 3) 算某个月的指标（首次会自动补该期间的同步批次）
python scripts/run_metric_calc.py --code retail_outbound_untaxed_amount --period 2026-08
```

`app_secret` 与 `access_token` 落库前用 `CryptoUtil`（Fernet）加密，接口只返回 `has_secret`/`has_token`。

## 6. 注意事项

- 淘系、拼多多平台单据的**价格类字段不下发**（文档原文），这些平台的出库单金额会是 0，需要走奇门/方舟另行对接。
- 分销+订单、线上发货订单不产生销售出库单，取不到数属正常。
- 部分或全部取消：`Delete`（发货前作废）、`Cancelled`（发货后撤销）不计入已出库。
- 按时间翻页存在数据变动导致漏单的可能，文档推荐 `start_ts` 增量方式；月度指标场景已用「7 天分段 + 出库时间」控制影响，如需严格一致可再切 `start_ts`。

## 7. 常见错误码

| code | 含义 | 处理 |
| --- | --- | --- |
| 10 | 无效签名 | 核对 `app_secret` 与 `app_key` 是否配对 |
| 100 | access_token 超时 | 重新授权拿新 token |
| 110 | IP 不在白名单 | 报错信息里会给出出口 IP，加到开放平台后台「应用详情 - IP白名单」；换机房后要同步更新 |
| 140 | 参数不符合规范 | 也可由 `app_key` 无效引起；确认用的是正式环境地址 `openapi.jushuitan.com` |
| 199 / 200 | 并发（5/秒）、频次（100/分钟）超限 | 客户端已自动退避重试，无需处理 |

排查顺序建议：先 `python scripts/jushuitan_check.py ... --period <上月>` 直连自检，再落库跑指标。

## 7.1 非淘系订单查询（订单查询 docId=22）

淘系订单走奇门，非淘系订单直接走聚水潭「订单查询」：

```
POST https://openapi.jushuitan.com/open/orders/single/query
```

关键约束：

- 该接口**不返回淘系和拼多多订单**；淘系走奇门，拼多多走方舟；
- 时间条件 `modified_begin` / `modified_end` 间隔不超过 **7 天**；
- `date_type`：`0` 修改时间、`2` 订单日期、`3` 发货时间；
- `page_size` 最大 **100**；
- 返回结构为 `data.orders`，分页字段 `has_next` / `page_count`；
- `status` 常用值：`WaitConfirm`（已付款待审核）、`Delivering`（发货中）、`Sent`（已发货）、
  `Question`（异常）、`Cancelled`（取消）。

同步到零售订单表：

```bash
cd backend

# 按月同步（按修改时间；首次补历史可加 --date-type 2 按订单日期）
python scripts/sync_jushuitan_orders.py --name "聚水潭默认连接" --period 2026-10

# 指定区间（单段超过 7 天会自动拆分）
python scripts/sync_jushuitan_orders.py --source-id 1 \
  --begin "2026-10-01 00:00:00" --end "2026-10-07 23:59:59" --date-type 0

# 只取数不写库
python scripts/sync_jushuitan_orders.py --name "聚水潭默认连接" --period 2026-10 --dry-run

# 每日定时任务：最近 7 天（按修改时间）
python scripts/sync_jushuitan_orders.py --name "聚水潭默认连接" --recent-days 7 --date-type 0
```

订单写入 `retail_order`，来源为 `jushuitan`，页面「开放接口 → 零售订单同步」可见。
默认不回放指标；需要时加 `--publish-metric`，但要注意不要与销售出库口径重复。

建议每日定时拉取最近 7 天（`--date-type 0`），更新 `WaitConfirm` → `Delivering/Sent` 等状态变化。

### 7.2 自动同步频率

后端启动后会自动注册两个任务：

| 任务 | 频率 | 范围 | 作用 |
| --- | --- | --- | --- |
| 增量同步 | 每 **10 分钟** | 最近 30 分钟 | 新订单、状态/金额变更 |
| 补偿同步 | 每天 **00:00 / 07:00 / 12:00 / 18:00** | 最近 7 天 | 补齐延迟变动、漏单 |
| 售后增量 | 每 **10 分钟** | 最近 30 分钟 | 退货退款新增/状态变化 |
| 售后补偿 | 每天 **00:00 / 07:00 / 12:00 / 18:00** | 最近 7 天 | 补齐退款完成、金额变化 |

任务写入 `retail_order`，页面「开放接口 → 零售订单同步」查看；不会自动回放指标。

可在 `backend/env/.env.prod` 调整：

```
RETAIL_ORDER_SYNC_INTERVAL_MINUTES=10
RETAIL_ORDER_SYNC_LOOKBACK_MINUTES=30
RETAIL_ORDER_SYNC_MAX_ROWS=20000
# RETAIL_ORDER_SYNC_CONNECTION_ID=1
# 零售金额税率（%）：接单未税/实退未税 = 含税 ÷ (1 + 13/100)
RETAIL_TAX_RATE=13
# 「货物出货」判定状态（逗号分隔），默认只算 Sent（已发货）
RETAIL_SHIPPED_STATUSES=Sent
```

修改后重启后端生效。

### 7.3 店铺查询（平台 + 店铺）

接口：`POST https://openapi.jushuitan.com/open/shops/query`（docId=1）

请求 `biz`：

```json
{"page_index": 1, "page_size": 100, "shop_ids": []}
```

返回 `data.datas[]`，常用字段：

| 字段 | 含义 |
| --- | --- |
| `shop_id` | 聚水潭店铺编号（订单查询/同步用这个） |
| `shop_name` | 聚水潭店铺名称 |
| `shop_site` | 平台/站点，如「淘宝天猫」「小红书」「商家自有商城」 |
| `platform_shop_name` | 平台店铺名称 |
| `session_status` | 授权状态：0 未授权、1 已过期、2 已授权、3 无需授权 |
| `session_expired` | 授权过期时间 |
| `co_id` | 公司编号 |
| `nick` | 授权账号 |
| `group_name` | 店铺分组 |

导出当前连接下的全部店铺：

```bash
cd backend
python scripts/list_jushuitan_shops.py --name "聚水潭默认连接" --output shops.csv
```

也可以 `--json` 直接查看。店铺查询返回的 `shop_site` 可用于区分平台；订单查询接口本身不返回淘系/拼多多订单
（淘系走奇门，拼多多走方舟）。

店铺/平台名称会写入 `retail_shop`（唯一键 `source + shop_id`），字段：
`shop_id`、`shop_name`、`shop_site`、`platform_shop_name`、`session_status`、
`session_expired`、`co_id`、`nick`、`group_name`、`synced_at`。

```bash
# 立即同步到数据库
python scripts/sync_jushuitan_shops.py
```

后端每天 **02:05** 自动同步一次店铺；平台店铺分析可用：

```sql
SELECT o.period_value, s.shop_site, s.shop_name, SUM(o.buyer_paid_amount)
FROM retail_order o
LEFT JOIN retail_shop s ON s.shop_id = o.shop_id AND s.source = 'jushuitan'
GROUP BY o.period_value, s.shop_site, s.shop_name;
```

管理端页面也可手动同步：**开放接口 → 零售订单同步 → 右上角「同步店铺」**（权限
`module_retail:shop:sync`）。同步后可直接用于平台/店铺分析。

### 7.4 售后/退货退款（docType=9&docId=38）

接口：`POST https://openapi.jushuitan.com/open/refund/single/query`

关键约束：

- **不返回淘系售后单**（拼多多仅近 3 个月）；淘系走奇门推送
  `POST /open/v1/retail/aftersales/sync`；
- 时间窗 `modified_begin` / `modified_end` 间隔不超过 **7 天**（客户端自动分段）；
- `date_type`：`0` 修改时间、`1` 创建时间、`2` 确认时间；
- `page_size` 最大 **50**；
- `is_get_promotion=true`（默认）才返回营收小计字段。

金额口径（表 `retail_after_sale.actual_refund`）：

```
实退金额 = freight(卖家应退运费) + refund(商品应退) - payment(补偿) - free_amount(优惠/差额)
```

请求字段速查：

| 字段 | 含义 | 落库列 |
| --- | --- | --- |
| `as_id` | 售后单号（唯一键） | `as_id` |
| `outer_as_id` | 平台售后单号 | `outer_as_id` |
| `so_id` / `o_id` | 线上单号 / 内部单号 | 同名列 |
| `shop_id` / `shop_name` | 店铺 | 同名列 |
| `type` / `status` / `shop_status` | 售后类型 / 状态 / 平台状态 | 同名列 |
| `as_date` / `modified` / `confirm_date` | 申请 / 修改 / 确认时间 | `as_date` / `modified_time` / `confirm_date` |
| `refund` / `freight` / `payment` / `free_amount` | 金额组成 | 同名列 + `actual_refund` |
| `buyer_paid_amount` / `seller_income_amount` | 营收小计 | 同名列 |
| `items[]` | 售后明细（`asi_id`、`sku_id`、`qty`、`r_qty`、`amount`） | `retail_after_sale_item` |

期间归属：`as_date` → `created` → `modified` → `confirm_date`，取第一个可用时间归到 `YYYY-MM`。

手动同步（管理端同样有按钮「同步聚水潭售后」）：

```bash
cd backend

# 按期间
python scripts/sync_jushuitan_refunds.py --name "聚水潭默认连接" --period 2026-10

# 最近 7 天（适合每日补偿）
python scripts/sync_jushuitan_refunds.py --name "聚水潭默认连接" --recent-days 7

# 只取数不写库
python scripts/sync_jushuitan_refunds.py --name "聚水潭默认连接" --period 2026-10 --dry-run
```

写入 `retail_after_sale` / `retail_after_sale_item`，页面
**开放接口 → 零售订单同步 → 退款售后** 可见，可按期间/店铺/单号/类型/状态筛选。

## 8. 调度与期间结转

| 时间 | 动作 | 说明 |
| --- | --- | --- |
| 每天 02:00 | 聚水潭同步（`0 0 2 * * ?`） | 按**当月**出库时间拉取，批次落到 `meta_sync_run` |
| 每天 02:30 | 指标批次重算当期（`metric/schedule.py` + `metric/batch.py`） | 按依赖分层重算**当月**累计值，写入新的 `calc_version` |
| 每月 1 日 02:30 | 上期结转 | 先**强制重拉**上月批次，再重算上月 |

为什么必须有「上期结转」：月指标的当月值最后一次刷新发生在月末 02:30，之后当月不再重算；
若不在次月 1 日补算，**月末最后一天白天的出库单会永久缺失**。结转逻辑见
`engine.refresh_period_batches()`（与 `_ensure_period_batches` 不同，它不判断「已有批次就复用」）。

指标之间有依赖（如汇总/比率指标引用组成指标），批次任务按 `metric_def.measures` 声明的依赖
**拓扑分层**执行：组成指标所在层先跑、依赖它的派生指标后跑，同层并发。运行期还会校验组成指标
「当天已算过」，不满足就先补算（`engine._ensure_component_values`）。
查看当前分层顺序：`python scripts/check_metric_deps.py`。

手动回补任意历史月份：

```bash
python scripts/run_metric_calc.py --code retail_outbound_untaxed_amount --period 2026-01
```

该命令会在缺少该期间批次时自动补拉数据，因此历史月份可以逐个补齐。
