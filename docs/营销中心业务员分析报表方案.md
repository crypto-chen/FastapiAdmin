# 营销中心业务员分析报表 · 建设方案（v0.1 草案，待确认）

> 目标：按 **年月 × 业务员** 统计「营销中心业务员分析指标」共 50 项。
> 数据来源：CRM 明细接口（`orderAnalyze` / `orderShipments`）+ 已有公司口径指标 + 待补数据源。
> 交付形态：**本系统作为数据中台 / 指标计算层，产出指标经开放接口供其他系统调用**（不自建业务报表）。
> 状态：**已交付 G1 组前 3 个指标（STF-13/14/15）**，见 §9；其余按 §6 分期推进。

## 0. 一句话结论

平台（核算指标系统）已有「期间 × 组织 / 部门」的指标引擎和 118 个**公司口径**指标；
本次要新增的是**「业务员」这一维度**——用 CRM 明细接口按 `create_id` 聚合，写进既有结果表
`metric_value`（已预留 `person_id` 列）。50 个指标里 **14 个用现有两份接口就能做**，
其余 36 个卡在 4 类数据源 / 规则上（见 §4）。

**交付物是开放接口，不是页面**：外部系统用现成的 `POST /open/v1/metrics/query` 按
`period_type=month` + `level=person` 取「年月 × 业务员」的指标值；
系统内的报表页降级为**内部核对 / 穿透**的可选工具（P0 可不做）。

| 能力 | 落点 |
| --- | --- |

| CRM 连接器 | `crm_connection`，GET + 无需鉴权，已接 30+ 个 `/hs` 接口（订单 / 报价 / 出货 / 下推 / 工时 / KPI） |

## 2. 本次新增的三个技术改动点（关键）

1. **取数**：CRM 明细接口的 `data` 是**数组**，现有 `extract_payload_rows`
   （`backend/app/modules/metadata/sync.py:437`）只认 `Rows` / `datas`，
   会把行数记成 1、明细整体丢失 → 必须扩展支持 `data` 数组。
2. **计算**：现引擎产出「期间 × 组织 × 部门」，派生指标
   （`metric_ratio` / `metric_diff`）只出**公司整体一行** → 需支持 `group_by = person`，
   否则毛利率 / 达成率 / 复购率这类比率会算成公司值套到每个业务员身上。
3. **展示**：`matrix` 查询需新增 `level=person`；`metric_value` 建议补
   `person_code` / `person_name`（现在只有 `person_id`），否则报表要多查一次主数据。

## 3. 数据流（业务员维度）

```
CRM 明细接口（按整月取，内贸 type=1 / 外贸 type=2）
  → meta_sync_run.rows_json（按月落原始明细）
  → 指标计算：按 create_id 分组聚合
      过滤 status=384（剔除作废 522）
      金额：内贸 remove_taxes_freight（不含运费）/ 外贸 receivable_CNY
      拆分：order_type 1=批量 2=打样 3=零售
  → create_id → source_person.crm_id → master_person → 标准业务员
  → metric_value（period_value, person_id, person_code, person_name, value）
  → 报表 / 矩阵接口 + Excel 导出
  → 对账：Σ业务员 = 现有公司口径指标（接单未税 / 出货 / 下推 / 工时）
```

## 5. 技术方案细化

### 5.1 取数（元数据同步）

- 新增来源对象：`/hs/order/orderAnalyze`（type=1、type=2 各一条）与 `/hs/order/orderShipments`（同）。
- 请求模板：`{"type": 1, "month": "{{ now.strftime('%Y-%m') }}"}`；发货接口的 `month` 按**发货单审核月**口径。
- 同步任务：每天 02:00（早于指标 02:30）；历史回补用现成的
  `execute_meta_sync_job(job_id, period_value)` 按期间触发。
- 数据量估算：内贸约 1300 行 / 月、响应约 3.9MB → 24 个月约 90MB，可接受；建议只保留近 24 个月批次。
- 已知上游问题：`numbers` 参数后端 SQL 字段名写错（`t1.nubmer`）返回 500 →
  目前按「月 + type 全量拉、本地按 `order_number` 关联」处理，不阻塞；建议同步提给 CRM 侧修复。

### 5.2 计算（指标引擎）

- 新增取数类型：`crm_order_person_agg`（订单明细 → 业务员）、`crm_shipment_person_agg`（发货明细 → 业务员）。
- 配置项：`source_object_code`、`type`、`period_field`（`createtime` / `check_date`）、
  `row_filters`（如 `status=384`）、`amount_terms`、`order_type_split`、
  `group_by=person`、`person_field=create_id`。
- 派生指标支持 `group_by=person`：比率 / 差额 / 折算按业务员分别计算。
- 业务员映射：`create_id` → `source_person.crm_id` → `master_person`；
  未映射的落到「未映射业务员（CRM uid）」行，**不丢数**。

### 5.3 存储

- P0（先跑通）：明细留在 `meta_sync_run.rows_json`，结果写 `metric_value`；
  加 `person_code` / `person_name` 列 + 索引。
- P1（建议）：建明细表 `crm_order_detail` / `crm_shipment_detail`（一行一单），
  支撑数据穿透（`metric_trace.dwd_row_id`）与多指标复用。

### 5.4 对外输出（指标开放接口）

本系统是**数据中台 + 指标计算层**，业务员指标的交付走既有开放接口，不新建业务页面。

- 入口不变：`POST /open/v1/metrics/query`（应用凭证换取令牌 → 批量取数），
  支持长表 / 宽表 / `total_only` 合计三种形态。
- 新增维度：`level` 增加 **`person`**；返回行补 `person_code` / `person_name`（业务员编码、姓名）。
- 新增过滤：`person_codes`（业务员编码，空 = 全部），与现有 `org_codes` 同风格。
- 新增应用权限：`allow_person_detail`（是否允许查业务员明细），与现有 `allow_dept_detail` 一致。
- 返回字段：`period_value` + `person_code` + `person_name` + `metric_code` + `value` + `calc_version` + `calc_time`
  （宽表则每个指标一列），外部系统可直接落库或做同比 / 环比。
- 文档：`scripts/gen_metric_api_doc.py` 从数据库自动生成，
  指标数与维度变化后重跑即可刷新《指标接口清单与调用方案》。
- 内部核对页（**已就绪**）：`指标中心 → 指标结果`（路由 `/metric/value`）层级筛选多一个
  「业务员明细」，表格自动多显示一列「业务员」（行 = 业务员、列 = 指标），用于对账与穿透。

## 8. 验收标准

1. **对账通过**：Σ业务员 = 现有公司口径指标（接单未税 / 出货 / 下推 / 工时），差异 ≤ 0.5%。
2. **可穿透**：任一业务员任一指标可下钻到订单 / 发货明细行。
3. **可回补**：任意历史月份可重算，保留 `calc_version` 版本。
4. **开放接口可用**：`POST /open/v1/metrics/query` 传 `level=person` 能取到
   「年月 × 业务员」长表 / 宽表 / 合计，且 `person_codes` 过滤、`allow_person_detail` 开关生效。

> 报价毛利率 77.62%（（未税 − 料工费）÷ 未税）vs 公司指标 51.11%（`getQuoteProfitRate` 直接返回值）。
> **加工费未计入**：接口的 `material_labor_cost` = `materialCost × qty`（含附件费、不含 `processCost`），
> 因此当前毛利率偏高；待 CRM 侧改为 `(materialCost + processCost) × qty` 后本系统自动按新口径取数。

### 9.3 对外接口

`POST /open/v1/metrics/query` 新增：

- `level=person`（需应用开启 `allow_person_detail`）；`level=org` 自动排除业务员行。
- 过滤：`person_ids`（**业务员主ID** = 内部标准人员 `master_person.id`）/ `person_codes`（CRM 用户名）。
- 返回行与宽表新增 `person_id` / `person_code` / `person_name`；`summary` 新增 `person_count`。
- **取合计用 `total_only=true`**：此时（含 `level=person`）直接返回公司合计层，
  不会把业务员行相加 —— 平均值（下推周期）、去重计数（老客户数）相加会算错。
- **粒度是「一个业务员一行」**：各行是该业务员自己的合计（内贸 + 外贸按业务员合并），
  互不相等、也不含公司总计；公司合计行只存在于 `metric_value` 内部（供派生指标与对账用），
  `level=person` 查询不会返回它。
- 实测：`metrics=[STF-13,STF-14,STF-15] & level=person & format=wide` → 58 行业务员宽表，
  `summary.total = 17,194,769.13`（三项合计）。
