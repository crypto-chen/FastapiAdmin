# 指标开放接口（Open API）设计方案

> 版本：v1.0（已实现）
> 日期：2026-09-28
> 状态：**已按第 7 节确认结论开发完成**，对接文档见 `docs/指标开放接口对接说明.md`
> 目标：把已计算的指标结果（`metric_value`）以标准 HTTP 接口开放给外部系统（BI、ERP、CRM、报表工具、Excel/脚本）只读调用。

## 0. 已确认结论（2026-09-28）

| # | 决策项 | 确认结果 |
|---|--------|----------|
| 1 | 鉴权方式 | 应用凭证换 Token（client_credentials），业务接口带 `Authorization: Bearer` |
| 2 | 指标开放范围 | **默认全部启用指标可读**，不做逐指标白名单 |
| 3 | 数据层级 | **默认只给组织合计**（`level=org`）；部门/客户明细需按应用单独开启 |
| 4 | 返回结构 | 默认长表，可通过 `"format": "wide"` 取宽表 |
| 5 | 前端管理界面 | 一并交付：接入应用管理页 + 调用日志页 |

---

## 1. 设计结论（先看这一段）

1. 新增独立路由前缀 `/open/v1`，**不挂在现有 `/api/v1` 下**，与管理端接口物理隔离，便于网关只放行 `/open/**`。
2. 鉴权采用 **应用凭证换 Token（client_credentials）**：外部系统用 `app_id + app_secret` 换短期 `access_token`，再以 `Authorization: Bearer` 调用业务接口。
3. 授权粒度是 **应用级白名单**：一个外部应用只能读「被授权的指标 + 被授权的组织 + 被允许的维度层级」。
4. 只读，复用 `metric_value`（已算好的结果），**不在开放接口里做实时计算**；需要最新数据时由外部系统调「触发重算」接口（默认不开放，需单独授权）。
5. 响应体沿用现有 `{code, msg, data, success}` 结构，但 `data` 里额外带口径信息（`calc_version` / `calc_time` / `unit`），让外部系统能判断数据新鲜度。

## 2. 与现有代码的衔接

| 事项 | 现状 | 开放接口怎么用 |
|------|------|----------------|
| 指标定义 | `metric_def`（`code` 唯一、`name`、`period_type`、`sensitivity`、`dimensions`、`measures`、`status`） | 作为开放目录与授权对象，授权用 `code` 而不是 `id` |
| 指标结果 | `metric_value`（`metric_id`、`period_type`、`period_value`、`org_id`、`dept_id`、`dept_code`、`dept_name`、`value`、`calc_version`、`calc_time`、`batch_id`） | 直接查询，默认只返回最新 `calc_version` |
| 期间格式 | 月指标 `YYYY-MM`，日 `YYYY-MM-DD`，年 `YYYY` | 请求参数沿用同一格式 |
| 组织/部门 | `master_org`（`code`/`name`/`parent_id`）、`master_dept`（组织内 `code` 唯一） | 组织用 `org_code` 对外，部门维度返回 `dept_code`/`dept_name` |
| 组织合计行 vs 明细行 | 组织合计行 `dept_code IS NULL`；核算维度明细行 `dept_code` 非空 | 由 `level` 参数翻译，外部系统不用理解 NULL 语义 |
| 权限体系 | 管理端是 RBAC + JWT + Redis 会话 | 开放接口**不复用**用户会话，独立应用表 + 独立 Token，避免外部系统拿到管理端身份 |
| 响应封装 | `SuccessResponse` / `ErrorResponse` / `ResponseSchema` | 复用，保证错误码风格一致 |
| 路由注册 | `backend/app/api/v1/routers.py` 的 `DOMAIN_CONTROLLERS` | 新增 `backend/app/api/open/v1/routers.py`，在 `create_app()` 里单独挂载 |

## 3. 鉴权方案

### 3.1 推荐方案：应用凭证换 Token（client_credentials）

```
POST /open/v1/auth/token
Content-Type: application/json

{ "app_id": "bi_report", "app_secret": "******" }
```

```json
{
  "code": 0,
  "msg": "获取令牌成功",
  "success": true,
  "data": {
    "access_token": "eyJhbGciOi...",
    "token_type": "Bearer",
    "expires_in": 7200
  }
}
```

业务接口统一带 `Authorization: Bearer <access_token>`。

理由：

- 外部系统只需保管一对凭证，不用每个请求做签名；接入成本最低。
- Token 有有效期，可被吊销（Redis 黑名单 / 应用停用即失效），泄露影响面可控。
- 与本项目已有的 JWT + Redis 机制一致，运维不需要引入新组件。

### 3.2 备选方案：请求签名（HMAC-SHA256）

每个请求带 `app_id`、`timestamp`、`nonce`、`sign`（`sign = HMAC_SHA256(app_secret, 排序后的参数串)`）。

适用场景：不允许存 Token 的批处理/离线脚本；或对方明确要求无状态签名。

**建议：先做 3.1，签名方式作为后续可选项再加，两者不叠加。**

### 3.3 应用表设计（新增）

```
open_client                    外部接入应用
├── app_id            String(64) 唯一    应用标识（对外暴露）
├── app_secret_hash   String(128)        密钥哈希（不可逆存储）
├── name              String(128)        应用名称（如「BI 报表平台」）
├── status            Integer            0 启用 / 1 停用
├── ip_whitelist      String(500)        允许的调用方 IP，逗号分隔，空=不限制
├── token_ttl_seconds Integer            令牌有效期，默认 7200
├── rate_limit        Integer            每分钟最大请求数，默认 600
├── expire_time       DateTime           凭证到期时间，空=长期
└── contact / description                联系人、用途备注

open_api_log                   调用审计
├── client_id / app_id / path / method
├── params(JSON) / status_code / cost_ms / client_ip / created_time
```

> `app_secret` 只在下发时明文展示一次；落库存哈希用于校验，不与管理端密码的 Fernet 加密混用。
>
> 指标开放范围按确认结论采用「默认全部启用指标可读」，因此**不建 `open_client_metric` 授权表**；
> 如后续需要按应用做指标白名单，再补该表并在 `_load_metrics` 中加过滤即可（预留扩展点）。

## 4. 接口清单（5 个）

| # | 方法 | 路径 | 说明 |
|---|------|------|------|
| 1 | POST | `/open/v1/auth/token` | 换取 access_token |
| 2 | GET | `/open/v1/metrics` | 本应用可读的指标目录 |
| 3 | POST | `/open/v1/metrics/query` | 主接口：批量按 指标 × 期间范围 × 组织 取数 |
| 4 | GET | `/open/v1/orgs` | 本应用可见的组织字典 |
| 5 | POST | `/open/v1/metrics/{code}/run` | 触发重算（默认不授权，需要时单开） |

### 4.1 `GET /open/v1/metrics` 指标目录

查询参数：`keyword`（按编码/名称模糊）、`page_no`、`page_size`（≤200）

```json
{
  "code": 0, "msg": "查询成功", "success": true,
  "data": {
    "page_no": 1, "page_size": 50, "total": 20, "has_next": false,
    "items": [
      {
        "code": "marketing_office_expense",
        "name": "营销中心办公费用",
        "period_type": "month",
        "unit": "元",
        "dimensions": ["dept", "customer"],
        "allow_dept_detail": false,
        "description": "科目 6601 当期借方发生额汇总"
      }
    ]
  }
}
```

### 4.2 `POST /open/v1/metrics/query` 批量取数（主接口）

请求：

```json
{
  "metrics": ["marketing_office_expense", "marketing_travel_expense"],
  "period_type": "month",
  "period_start": "2026-01",
  "period_end": "2026-09",
  "org_codes": ["01", "02"],
  "level": "org",
  "include_meta": true
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `metrics` | 是 | 指标标识数组，上限 20 个，可传系统指标编码或 Excel 科目编码（`excel_code`）；不可读的标识在 `errors` 中说明 |
| `period_type` | 否 | 默认 `month`；允许 `day`/`week`/`month`/`year` |
| `period_start` / `period_end` | 否 | 期间区间；不传取当前期间；区间上限 36 个期间 |
| `org_codes` | 否 | 不传 = 授权范围内的全部启用组织 |
| `level` | 否 | `org`（默认，只给组织合计）/ `dept`（只给核算维度明细）/ `all` |
| `total_only` | 否 | `true` 只返回合计（`totals`），不返回组织明细 `items` |
| `include_meta` | 否 | 默认 `true`，返回指标名称、单位、口径说明 |

响应（长表结构，一行一个「指标 × 期间 × 组织（× 维度）」，便于 BI 直接透视）：

```json
{
  "code": 0, "msg": "查询成功", "success": true,
  "data": {
    "period_type": "month",
    "level": "org",
    "calc_version_policy": "latest",
    "metrics": [
      { "code": "marketing_office_expense", "name": "营销中心办公费用", "unit": "元", "period_type": "month" }
    ],
    "items": [
      {
        "metric_code": "marketing_office_expense",
        "excel_code": "EXP-01-a",
        "period_value": "2026-08",
        "org_code": "01",
        "org_name": "永锢科技",
        "dept_code": null,
        "dept_name": null,
        "value": 12345.67,
        "calc_version": 3,
        "calc_time": "2026-09-28 02:30:11",
        "batch_id": "202609280230"
      }
    ],
    "summary": { "item_count": 36, "metric_count": 2, "period_count": 9, "org_count": 2 }
  }
}
```

要点：

- 金额单位为元，保留 4 位小数（与 `metric_value.value` 一致）。
- 只返回存在的行；某组织某期间无数据则不补 0，由调用方判断（`fill_missing` 列为后续可选）。
- 不传 `calc_version` 时取该指标该期间的最新计算版本；后续可选支持指定历史版本复算口径。
- 单次默认上限 5000 行，超出按 `page_no`/`page_size` 翻页，或改用 CSV 导出接口（后续可选）。
- 只要一个总数时用 `total_only=true`：按「指标 × 期间」汇总到 `totals`，`items` 为空，避免外部系统自己求和。

### 4.3 `GET /open/v1/orgs` 组织字典

返回授权范围内的组织，字段：`org_code`、`org_name`、`parent_code`、`level`；可选 `tree=true` 返回树形。

### 4.4 错误策略

「部分失败不静默」：请求多个指标时，未授权或不存在者不返回数据，但在 `data.errors` 中逐条说明，HTTP 仍返回 200。

```json
{
  "code": 0, "msg": "部分指标无权限", "success": true,
  "data": {
    "items": [],
    "errors": [ { "metric_code": "marketing_ar_balance", "reason": "未授权" } ]
  }
}
```

若 `metrics` 中全部不可读，则返回 HTTP 403 + 业务码 `40102`。

---

## 5. 错误码与限流

| 业务码 | HTTP | 含义 | 处理建议 |
|--------|------|------|----------|
| 0 | 200 | 成功 | — |
| 40100 | 401 | 未携带/无效/过期 Token | 重新换取 Token |
| 40101 | 403 | 应用已停用 / 已过期 / IP 不在白名单 | 联系管理员 |
| 40102 | 403 | 指标未授权 | 联系管理员加白名单 |
| 40103 | 429 | 超出调用频率 | 按 `Retry-After` 退避重试 |
| 40104 | 400 | 参数非法（期间格式、区间超限、指标数超限） | 修正参数 |
| 40105 | 500 | 服务内部错误 | 携带 `trace_id` 反馈 |

限流：按 `app_id` 计数，默认 600 次/分钟，用 Redis 计数器实现；超限返回 `40103` 与 `Retry-After` 头。响应头透出 `X-Request-ID`（项目已有链路 ID 中间件）用于排障。

## 7. 实现说明（与设计稿的差异）

确认后的 5 项决策见第 0 节；相对 v0.1 设计稿的落地差异如下：

1. 不建 `open_client_metric` 指标授权表（默认全部启用指标可读）。
2. 换令牌接口使用独立配额（30 次/分钟），不占用业务接口的每分钟调用配额。
3. 429 响应的建议等待秒数写在 `msg` 中（项目统一异常处理器不支持自定义响应头，故未设 `Retry-After`）。
4. `level=dept/all` 需应用开通「核算维度明细」，未开通时返回 `403 / 40102`，不静默降级。
5. 未映射到标准组织的合计行（`org_id` 为空）仅在应用未限制组织范围时返回，`org_code` 为 `null`。
