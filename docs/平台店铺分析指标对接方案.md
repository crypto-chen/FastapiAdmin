## 4. 可做指标的取值口径

### 4.1 平台与店铺

- 平台：`retail_shop.shop_site` 归一化：
  - `淘宝天猫` / `天猫` → 天猫
  - `京东` → 京东
  - `拼多多` / `拼多多店铺` → 拼多多
  - `抖音` / `抖音电商` → 抖音
  - `小红书`、`商家自有商城`、`有赞`、空值 → 其他
- 店铺：`retail_shop.shop_id`、`shop_name`；`shop_id=0` 的线下店铺单列“其他/线下”。
- 只统计纯零售时，按 `retail_order.source IN ('qimen','jushuitan')`，不要关联 CRM B2B 订单。

### 4.2 PLT-08 接单未税

订单金额优先级（订单头优先，避免组合装重复）：

```text
buyer_paid_amount > pay_amount > paid_amount
```

三者都为空时，才回退到明细合计：

```text
SUM(retail_order_item.buyer_paid_amount / seller_income_amount / amount)
```

未税：

```text
未税金额 = 含税金额 ÷ 1.13        （默认税率 13%，可用 RETAIL_TAX_RATE 调整）
```

已实现：零售页面「接单未税」= 买家实付合计 ÷ 1.13，接口 `summary.untaxed_amount_sum`
同值；明细行 `untaxed_amount` 为逐单未税（保留 2 位小数，四舍五入）。

口径：
- 期间：`retail_order.period_value`；
- 排除 `Cancelled`、`Delete`；`Question` 保留但单独标记；
- 接单量：该期间按 `shop_id + order_key` 去重计数；
- 税率：按平台/店铺配置，默认 13%；同一店铺所有期间保持一致。

### 4.3 PLT-09 货物出货未税

口径（2026-10-27 确认）：**订单状态已发货即算货物出货**，直接用零售订单表，不再单独取出库单。

```text
PLT-09 = SUM(retail_order.buyer_paid_amount WHERE status IN ('Sent')) ÷ 1.13
```

- 已发货：订单状态 `Sent`（`RETAIL_SHIPPED_STATUSES` 可配，例如加上 `Delivering` 把「发货中」也算进来）；
- 未发货（`WaitConfirm`/`Delivering` 未纳入时）不计；
- `Cancelled`/`Delete` 既不接入接单也不入出货；
- 期间与接单一致，用 `retail_order.period_value`（保证 PLT-08、PLT-09、PLT-11 同期同店可比）。

已实现接口：`GET /api/v1/retail/analysis/summary?period_value=2026-10`，返回
`items[]`（期间 × 店铺）与 `total`：

```json
{"period_value":"2026-10","shop_id":900001,"order_count":52,"shipped_order_count":41,
 "intake_untaxed":600.0,"shipment_untaxed":300.0,"refund_untaxed":-50.0,
 "net_shipment_untaxed":250.0,"return_rate":0.2}
```

页面对应：**零售订单同步 → 平台店铺分析**（列：接单未税 / 出货未税 / 退货未税 / 净额 / 退货率）。

指标中心也有独立页面：**指标中心 → 平台分析**（`/metric/platform`），
按「期间 × 平台 × 店铺」展示 PLT-xx 全字段，版式与「产品线分析」一致，
支持店铺明细 / 平台小计 / 全部三种聚合层级、字段多选、平台排行与字段说明。
接口：`GET /api/v1/platform/{fields,periods,platforms,page,stats}`。

> 旧指标 `retail_outbound_untaxed_amount`（聚水潭销售出库查询）保留不变，口径是「按出库时间」；
> 平台店铺分析统一走上面的「按订单期间 + 已发货」口径，两者不要混用。

### 4.4 PLT-12 / PLT-13 / PLT-23

```text
PLT-11 = 退货退款金额（负数）
PLT-12 = PLT-09 + PLT-11
PLT-13 = PLT-12 × 10%
PLT-23 = PLT-13 × 4%
```

已实现（`GET /retail/analysis/summary`）：`net_shipment_untaxed`（PLT-12）、
`settlement_income_untaxed`（PLT-13，比例由 `RETAIL_SETTLEMENT_RATE` 控制，默认 10）。
页签「平台店铺分析」同步展示「对外出货净额」「营销结算收入」两列。

PLT-11 取数（2026-10-27 确认口径：**取消单 + 发货后申请退款**）：

```sql
-- ① 取消单：订单状态 Cancelled，金额全额计入退货
SELECT period_value, shop_id, SUM(buyer_paid_amount) AS amount
FROM retail_order
WHERE is_deleted = 0 AND status IN ('Cancelled')
GROUP BY period_value, shop_id;

-- ② 发货后申请退款：售后单能匹配到订单，且订单状态已发货（Sent）
--    匹配不到订单的售后单仍计入（避免淘系订单未推送导致漏退款）
SELECT a.period_value, a.shop_id, SUM(a.actual_refund) AS amount
FROM retail_after_sale a
LEFT JOIN retail_order o
       ON o.shop_id = a.shop_id AND o.so_id = a.so_id AND o.is_deleted = 0
WHERE a.is_deleted = 0
  AND (o.id IS NULL OR o.status IN ('Sent'))
GROUP BY a.period_value, a.shop_id;

-- PLT-11（负数）= -(① + ②) ÷ 1.13
```

- 非淘系：聚水潭售后接口 `RefundQuery`（docId=38）每 10 分钟增量 + 每日 7 天补偿；
- 淘系：奇门推送 `POST /open/v1/retail/aftersales/sync`（免鉴权）；
- `actual_refund = freight + refund - payment - free_amount`；
- 未税口径：`actual_refund ÷ 1.13`（默认 13%，`RETAIL_TAX_RATE` 可配）；
- 未发货订单上的售后（订单仍是 `WaitConfirm`/`Delivering`）不计入，避免和取消单重复；
- 取消状态可用 `RETAIL_CANCELLED_STATUSES` 调整（默认 `Cancelled`）。

接口已实现：`GET /retail/analysis/summary` 的 `total.cancelled_untaxed`（取消）、
`total.refund_untaxed`（发货后售后）、`total.return_untaxed`（PLT-11 合计）。

> 退货率 PLT-37 = |PLT-11| ÷ PLT-12；当 PLT-12 ≤ 0（退货大于出货）时改用 PLT-09 作分母。

### 4.5 PLT-38 客单价

```text
PLT-38 = PLT-08 ÷ 接单量
```

接单量：

```sql
COUNT(DISTINCT order_key)
FROM retail_order
WHERE period_value = :period
  AND status NOT IN ('Cancelled', 'Delete')
```

### 4.6 PLT-44 复购率

客户键：

```text
buyer_id 优先；为空时用 shop_buyer_id
```

建议口径：

```text
复购客户数 = 当前期间下单客户中，过去 12 个月累计订单数 ≥ 2 的客户数
总客户数 = 当前期间下单客户数
PLT-44 = 复购客户数 ÷ 总客户数
```

排除游客/空/`****`/脱敏值；如果要按月复购，可把窗口改为“当前期间 ≥ 2 单”，但需业务确认。

### 4.7 PLT-03 / PLT-04 映射

需要两张维表：

```text
dim_shop_operator(shop_id, operator_code, operator_name, effective_from, effective_to)
dim_sku_product_line(sku_id, i_id, product_line_code, product_line_name)
```

- 运营人员由电商/CRM 维护，订单表本身没有运营字段。
- SKU→产品线来自 ERP 商品字典；组合装要按 `raw.sku_type`/`src_combine_sku_id` 选择组合装或拆分件，不能两边都计。

**CRM 产品字典能否直接对上？**

当前实测（本地库，2026-10）：

| 项 | 数量 |
| --- | --- |
| CRM 产品型号字典 | 523 个型号 |
| CRM 产品分类 | 52 个分类 |
| 零售明细唯一主 SKU（剔除螺丝、运费、测试） | 903 个 |
| 名称前缀可唯一命中 CRM 型号 | 491 个（54.4%） |
| 名称前缀命中多个型号，需要人工确认 | 131 个（14.5%） |
| 未命中 CRM 型号 | 281 个（31.1%） |
| 有候选（唯一+多候选） | 622 个（68.9%） |

结论：
- **不能直接用 `retail_order_item.sku_id/i_id` join CRM 型号字典**：零售 SKU 是 `BCP...` 编码，CRM 字典的键是 `model`（如 `J27A`、`M08`、`K21C`）。
- 商品名称的前缀能匹配大部分主产品（如 `K21C-160-55...` → `K21C`），但 `J27` 可能对应 `J27A`，`J16` 可能对应 `J16A/J16B`，存在歧义。
- 未命中的 281 个多是尺寸开头的配件/支架/上下盖，或 ERP 自定义件，需要 ERP 物料/BOM 映射或人工维护。

建议新增映射表：

```text
dim_sku_product_line
  sku_id / i_id
  crm_model_id
  crm_model_name
  product_line_code
  product_line_name
  match_type（exact/name_prefix/manual/unmatched）
  confidence
```

初始化流程：
1. 用 `retail_order_item.i_id/sku_id` 精确匹配 CRM 型号（命中很少）。
2. 用商品名称前缀匹配 CRM 型号；唯一命中自动写入，多个候选标记待确认。
3. 人工确认 131 个歧义 SKU；未命中的 281 个按 ERP 物料/BOM 或业务规则补。
4. 未分类项统一落到“其他”，不要强行归入 7 大类。

CRM 分类到目标 7 大类还需要一层业务映射：

```text
CRM 产品分类（52 个） → 铝壳/机箱/功放/铝型材外壳/防水外壳/防护外壳/钣金外壳/其他
```

因此 PLT-04 可以做，但必须先建 `dim_sku_product_line`，不能在取数 SQL 里临时用名称 `LIKE` 猜。

| 3（3～5 天） | 店铺→运营、SKU→产品线、PLT-03/04/44 | 平台店铺分析页 |
| 4（3～5 天） | 平台费/推广费/快递/售后录入，PLT-14～21/24/25 | 边际贡献 |
| 5（3～5 天） | 固定费用分摊、薪酬/考勤、回款、线索，PLT-22/26～31/36/39～43 | 完整结算/ROI |

## 8. 需要业务确认

1. **税率**：按平台还是按店铺配置？默认 13% 是否适用所有店铺？
2. **退款金额**：聚水潭售后接口能否提供金额；如果不能，是否接受平台账单/手工导入？
3. **运营人员**：谁维护 `shop_id → 运营人员` 映射？
4. **固定费用**：PLT-22 按收入、面积还是人数分摊？
5. **复购窗口**：PLT-44 用“当前期间 ≥2 单”还是“过去 12 个月 ≥2 单”？

## 9. 纯零售需要注意

- PLT-08 只取 `retail_order`，不取 CRM B2B 订单；如后续要合并 B2B，必须另建口径，不能直接相加。
- 组合装订单同时存在组合装行和拆分件行，订单金额用订单头，SKU/产品线分析必须先选组合装或拆分件口径。
- 平台店铺主数据中的 `shop_id=0` 是线下店铺，平台分析时建议单列“其他/线下”。
