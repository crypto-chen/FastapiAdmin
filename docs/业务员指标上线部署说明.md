# 业务员指标上线部署说明（开发环境 → 服务器）

> 适用：把开发环境已完成的**业务员指标（16 个）+ 开放接口业务员维度**迁移到服务器。
> 部署形态：Docker Compose（`deploy.sh` + `docker/`），代码由本地/开发机上传，服务器上构建启动。
> 执行顺序：**备份 → 传代码 → 重建启动 → 建指标与任务 → 回补历史 → 开对接权限 → 校验 → 出对接文档**。

---

## 0.0 两种落地路线（先看这里）

本次改动分两类：**代码**（Python：取数引擎、开放接口业务员维度、CRM 客户端修复）与
**数据**（表字段、指标定义、来源对象、同步任务、权限开关）。数据部分可以全部用 SQL 完成，
但代码必须部署——否则服务器既算不出业务员指标，开放接口也不认识 `level=person`。

| 环节 | 纯 SQL 能否解决 | 说明 |
| --- | --- | --- |
| 取数引擎 / 开放接口 / CRM 客户端修复 | ❌ 必须传代码 | 后端 5 个模块文件 + 3 个迁移文件 |
| 表结构（`person_code` / `person_name` / `allow_person_detail`） | ✅ | `01_schema.sql`（幂等）或 `main.py upgrade --env=prod` |
| 指标定义 / 来源对象 / 同步任务（16 + 6 + 6 条） | ✅ | `02_defs.sql`（幂等，可重复执行） |
| 历史结果数据 | ⚠️ 有限 | 服务器上跑 `backfill_person_metrics.py` 从 CRM 重算（推荐）；`03_values.sql` 是开发机快照，仅作临时兜底 |
| 对接方权限开关 | ✅ | `02_defs.sql` 末尾的 `UPDATE open_client ...` |

SQL 脚本已随仓库生成在 `deploy/person-metrics/`（需要重新生成时）：

```bash
cd backend
python scripts/export_person_metrics_sql.py --with-values
```

**推荐组合（最稳）**：传代码 → `./deploy.sh`（启动时自动跑迁移）→ 执行 `02_defs.sql` → 跑 `backfill_person_metrics.py`。

**纯 SQL 组合**（服务器不方便跑脚本时）：传代码 → 依次执行 `01_schema.sql` → `02_defs.sql`（→ 可选 `03_values.sql`）→
新月份由每天 02:00 同步 / 02:30 计算自动补齐。

## 1. 上传代码

### 方式 A：整目录上传（推荐，最省心）


## 2. 前端构建 + 重建后端并启动

```bash
# ① 前端（本地构建后上传 dist，或服务器上构建）
cd frontend/web && npm install && npm run build
cp -r dist/* ../../docker/nginx/web/

# ② 服务器上重建并启动
cd /path/to/FastapiAdmin
./deploy.sh                 # 完整部署：校验 → 构建镜像 → 启动 → 健康检查
# 或只重建后端
cd docker && docker compose build backend && docker compose up -d --force-recreate backend
```

启动时后端会自动执行 `alembic upgrade head`（`app/scripts/initialize.py`），把上面 3 个迁移应用到服务器库；
同时 `app/__init__.py` 会把启用的同步任务重新挂到调度器。

## 4. 建业务员指标与同步任务

> **也可以直接执行 SQL**：跳过本节的 seed 脚本，改为在数据库客户端依次执行
> `deploy/person-metrics/01_schema.sql`（表结构，幂等）与 `02_defs.sql`（6 个来源对象 + 6 个同步任务 + 16 个指标定义 + 权限开关，幂等）。
> 两个文件都自带存在性判断，重复执行安全；执行末尾附带核对查询。
> 走 SQL 路线时**必须**再确认 `alembic_version` 已对齐（见 §3），否则后端下次启动会重复加列报错。

```bash

docker compose exec backend python scripts/seed_crm_person_metrics.py \
  --base-url http://crmapi.yonggubox.com
```

脚本是幂等的（按 code 覆写），输出应包含 **16 个指标** 与 **6 个同步任务**：

| 来源对象 | 同步任务 Cron | 说明 |
| --- | --- | --- |
| `/hs/order/orderAnalyze?type=1` `/type=2` | `0 0 2 * * ?` 每天 02:00 | 内贸 / 外贸订单明细（约 1.3k 行/月） |
| `/hs/order/orderShipments?type=1` `/type=2` | `0 0 2 * * ?` 每天 02:00 | 内贸 / 外贸发货明细 |

## 5. 回补历史数据

服务器上没有这些明细批次，必须按期间取数 + 重算（脚本会自动跳过已存在的批次）：

```bash
cd /path/to/FastapiAdmin/docker

# 建议回补 2025-01 至今（每月 6 个来源取数 + 16 个指标重算，约 2~5 分钟/月）
docker compose exec backend python scripts/backfill_person_metrics.py \
  --start 2025-01 --end 2026-09

# 只补最近一个月
docker compose exec backend python scripts/backfill_person_metrics.py --start 2026-09 --end 2026-09
```

输出结尾会打印 `{"periods": [...], "metric_count": 16, "failed": []}`；若有 failed 会以非 0 退出码结束，便于脚本判断。

> 说明：客户列表是快照口径，脚本只在开始时同步一次，历史期间复用同一份快照（与其他期间口径一致）。

## 7. 上线校验

```bash
cd /path/to/FastapiAdmin/docker

# ① 结果行数与合计（应输出 16 个指标的合计值与业务员个数）
docker compose exec -T mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" fastapiadmin -e "
SELECT d.excel_code, d.name,
       SUM(CASE WHEN v.person_code IS NULL THEN v.value ELSE 0 END) AS total,
       SUM(CASE WHEN v.person_code IS NOT NULL THEN 1 ELSE 0 END) AS persons
FROM metric_value v JOIN metric_def d ON d.id = v.metric_id
WHERE d.category='营销中心-业务员' AND v.period_value='2026-09'
  AND v.calc_version = (SELECT MAX(calc_version) FROM metric_value m
                        WHERE m.metric_id=v.metric_id AND m.period_value=v.period_value)
GROUP BY d.id ORDER BY d.excel_code;"

# ② 开放接口实测（用对接方应用换令牌后取数）
curl -X POST "https://<对外域名>/open/v1/metrics/query" \
  -H "Content-Type: application/json" -H "Authorization: Bearer <token>" \
  -d '{"metrics":["STF-13","STF-10"],"period_start":"2026-09","period_end":"2026-09","level":"person","format":"wide"}'
```

开发环境基准值（2026-09，可用于比对）：STF-13 = 7,932,426.27（53 人）、STF-10 = 607（52 人）、
STF-47 = 9,878（62 人）、STF-49 = 8.362%。

> **注意**：CRM 是实时业务库，历史月份的数据会随后续改单变化，所以服务器回补出的历史值与开发机可能存在小差异，
> 属正常现象；同一次取数内各指标自洽（新+老客户=接单未税 等）才是关键校验。

## 9. 定时任务与日常运行

- 每日 02:00 同步 CRM 明细（订单 / 发货 / 报价；客户列表每周一）；02:30 按依赖分层重算**当月**全部指标。
- 每月 1 日自动**重拉上月批次并重算上月**（月末最后一天白天产生的单据不会丢）。
- 新增指标后无需改调度：批次任务扫「启用中的指标」，业务员指标自动纳入。

## 10. 回滚

1. **代码回滚**：恢复上一版本代码 → `./deploy.sh`（或 `docker compose up -d --force-recreate backend`）。
2. **指标下线**：`UPDATE metric_def SET status=1 WHERE category='营销中心-业务员';`（停用后不再计算、开放接口也不返回）。
3. **数据库回滚**：`docker compose exec backend python main.py ... ` 不适用，直接用第 0 步的备份恢复：
   ```bash
   docker compose exec -T mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" < /root/fastapiadmin_backup_YYYYMMDD_HHMM.sql
   ```
   （新增列可保留，不影响旧代码运行；旧代码不会写 `person_code`。）

## 11. 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 后端启动报 `Unknown column 'person_code'` | 迁移没应用：`docker compose exec backend python main.py upgrade --env=prod` |
| `docker compose exec backend python scripts/...` 报脚本不存在 | 代码没上传成功（或没重建镜像，容器内还是旧代码）：`docker compose build backend && docker compose up -d backend` |
| 业务员指标算出来是 0 | 该期间没有明细批次：先跑 `backfill_person_metrics.py`（或等 02:00 同步后重算） |
| 回补很慢 | 首月要拉 12 期订单明细（下推/出货类回看窗口），后续月份命中已有批次会快很多 |
| 接口 403 提示未开通业务员明细 | 第 6 步的 `allow_person_detail` 没开 |
| 同步任务没按点跑 | 重启后端让调度器重新挂载：`./deploy.sh restart`，或看「元数据管理 → 元数据查看 → 同步任务」是否启用 |
