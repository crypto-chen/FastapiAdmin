# 订单全链路数据方案（订单明细宽表 + 派生指标）

> 状态：方案已确认，待开发
> 确认日期：2026-10-13
> 确认结论：可变字段走 `extra` JSON；换来源后重算历史并保留版本；对外提供字段目录接口。
> ⚠️ 2026-10-13：CRM `orderAnalyze` 接口更新，新增成本字段的同时把响应从 117 个字段裁剪到 6 个，明细构建被阻断，详见 §11。

---

## 0. 已确认结论（先看这一段）

1. **不做成指标**：订单全链路是「一行一单」的明细，`metric_def` 的模型（指标×期间×组织/部门/业务员 = 一个数值）装不下 40+ 个字段。指标层继续只放聚合数值。
2. **两层架构**：明细层 `dwd_order_full_chain` 做底，指标层 `metric_def` / `metric_value` 从明细聚合。
3. **存储**：核心字段用物理列（订单号、期间、节点日期、主干金额、审计），**可变字段统一进 `extra` JSON**，加减字段零 DDL。
4. **字段定义走元数据注册表**：复用 `meta_standard_entity` / `meta_standard_field` / `meta_field_mapping`，字段与来源都是配置，不是代码。
5. **版本**：换口径/换来源后按新口径重算历史，`calc_version` 递增、不覆盖旧版本；查询默认取最新版本。
6. **对外**：`/open/v1/orders/*` 三个接口 —— 字段目录、明细增量拉取、单订单查询；外部只认 `field_code`，不认物理列名。

### 3.2 可变字段区 `extra`

所有会调整来源、会增删的字段都放这里，JSON 结构：

```json
{
  "size": "2U-250-655",
  "platform_code": "909",
  "platform_name": "独立站",
  "shop_code": "596",
  "shop_name": "海外自建站",
  "is_new": "2",
  "product_series_code": "17",
  "product_series_name": "机箱",
  "design_fee": 0.0,
  "deposit": 1638.0,
  "unit_cost": 42.56,
  "material_cost_unit": null,
  "gross_profit": null,
  "push_period": 8.86,
  "production_cycle": 9.4,
  "ship_cycle": 5.2,
  "full_cycle": 18.7,
  "mo_numbers": ["MO044165"],
  "cost_source": "order",
  "schema_version": "2026-10-13"
}
```

规则：

- **加字段**：注册表加一行 + 构建脚本认这个 `field_code`，零 DDL。
- **减字段**：注册表 `status=1`，历史值保留在 `extra` 里不删。
- **换来源**：改注册表映射 + 按新口径重算，表结构不动。
- **热点字段提升**：某个 `extra` key 查询频繁时，再加物理列 + MySQL 8 生成列/索引，属于性能优化、不是业务变更。

### 3.3 字段注册表（复用元数据表）

不新建表，直接用已有三张：

| 表 | 作用 | 用法 |
| --- | --- | --- |
| `meta_standard_entity` | 注册标准实体 | `code = order_full_chain`，`table_name = dwd_order_full_chain` |
| `meta_standard_field` | 声明字段 | `field_code` = 对外字段名，`data_type`、`is_dimension` / `is_measure` |
| `meta_field_mapping` | 来源映射 | 一个标准字段挂多个来源（主来源 + 兜底来源），`transform_type` / `transform_config` 描述取数规则 |

`meta_field_mapping.transform_config` 约定（扩展字段，向后兼容）：

```json
{
  "source_object_code": "/hs/order/orderAnalyze?type=1",
  "source_field": "remove_taxes_freight",
  "transform": "direct",
  "priority": 10,
  "fallback": [
    {"source_object_code": "/hs/order/orderAnalyze?type=2", "source_field": "receivable_CNY", "priority": 20}
  ],
  "effective_from": "2026-10",
  "effective_to": null
}
```

- `priority` 越小越优先，命中即停 → 这就是「报价单取不到就兜底取订单成本」的实现方式。
- `effective_from` / `effective_to` 支撑「换来源后按期间选生效口径」。

> 现状说明：`meta_source_field` / `meta_standard_field` / `meta_field_mapping` 目前由「字段映射」管理模块维护（含 `auto_match_field` 自动匹配），**尚未被计算引擎消费**。本方案的构建任务将是它们的第一个运行时消费者。

### 3.4 重算与版本规则

1. 每次构建按 `period_value` 计算，产出新的 `calc_version`（`max(calc_version) + 1`），**新增行、不覆盖**。
2. 查询/对外默认取每个 `order_number` 的最大 `calc_version`。
3. 旧版本保留期为 3 个版本（可配置），更早的版本按期间归档清理。
4. `data_quality_flag` 取值：

   | 标记 | 含义 |
   | --- | --- |
   | `ok` | 全字段取到 |
   | `cost_missing` | 成本字段为空（如 2025-12 之后的订单） |
   | `mo_unlinked` | 生产订单未关联上（BH 备货单、YF 打样单） |
   | `ar_customer_level` | 应收/逾期为客户维度，订单维度是按客户回填的 |

### 4.1 关键口径备忘

- **接单未税字段已改名（2026-10-13）**：内贸由 `remove_taxes_freight` 改为 **`amount`**，外贸仍是 `receivable_CNY`。同一订单 `DY202609-00001` 的 `amount` = 4831.86，与改名前的 `remove_taxes_freight` 完全一致，口径未变、只是换名。
- **成本字段是整单合计**：`material_cost_total`（材料费）与 `process_cost_total`（加工费）都是订单级金额，单位成本必须除以 `qty`。

  ```
  标准材料成本（单位） = material_cost_total ÷ qty
  标准单位成本        = (material_cost_total + process_cost_total) ÷ qty
  ```

  判定依据（2026-09 实数据，`PL202609-02634`）：数量 3000、接单未税 83628.32、材料费 12378.00、加工费 75213.00 → 成本合计 87591.00（成本率 104.7%，单位成本 29.20）。若按单件成本解释，该单成本合计会是 87591 × 3000，量级不成立。
- **成本覆盖（2026-09 实测）**：内贸 1178 / 1298（90.8%）、外贸 92 / 121（76.0%）。此前的 2025-12 起「成本全空」问题随本次接口更新已解除。
- **生产订单关联**：`PRD_MO.FSaleOrderNo` 就是 CRM 订单号，但成品/半成品行带物料后缀（`DY202609-00733-BCP1100686`），关联时取前两段。2026-09 实测 7111 行、覆盖率 85.2%；未命中的是 `BH` 备货单与 `YF` 打样单（CRM `orderAnalyze` 无对应记录）。

## 5. 构建任务

### 5.1 关联链路

```
orderAnalyze(内贸) ─┐
orderAnalyze(外贸) ─┴─→ 订单主表（一行一单）
                        ├─ orderShipments 按 order_number 关联 → 出货未税
                        ├─ PRD_MO 按 FSaleOrderNo(取前两段) 关联 → 生产工单/入库数量/生产周期
                        ├─ PRD_INSTOCK 按 FReqBillNo/需求单据关联 → 齐套入库
                        ├─ getReturnOrderDetail → 退货退款
                        ├─ AR_AgingAnalysis 按客户回填 → 应收余额/逾期天数
                        └─ getCusotmerList → 客户名称
                        ▼
                 dwd_order_full_chain
```

### 5.1.1 跨月明细的往后查找（2026-10-13 修复）

**问题**：发货、退货、生产订单都发生在**接单之后**，原先只读「订单所在期间」的批次，
跨月明细全部取不到。例：`DY202609-03163` 是 9 月接单、10 月发货，出货未税一直是空。

**修复**：这三类明细改成从订单期间起**往后查找**已存在的批次（`build.forward_rows()`）：

| 明细 | 往后窗口 | 说明 |
| --- | --- | --- |
| 发货明细 orderShipments | 12 期 | 行数小，窗口放宽 |
| 退货退款 getReturnOrderDetail | 12 期 | 同上 |
| 生产订单 PRD_MO | 3 期 | 批次大（约 7000 行/月），窗口收紧 |

每个期间只取**最新一次**成功批次，避免重跑产生的多批次重复计数。

**效果**（2026-09）：关联生产订单 1040 → **1260**；有出货未税 660 → **989**；
全量 25 期关联生产订单 18127 → **23400**。

**仍是空的**：`ship_date`（销售出库日期）取自 CRM 订单明细的 `chuhuo_date`，
部分订单 CRM 侧仍是 `chuhuo=2`（未标记出库）但发货明细已有记录——2026-09 有 162 单属于这种情况，
需 CRM 侧补标记；发货接口本身不返回日期。

### 5.2 幂等与回补

- 一次构建 = 一个期间，输入是该期间的所有来源批次，输出 `calc_version` 递增的新行。
- 回补历史：`python scripts/run_order_build.py --period 2026-09`（沿用 `run_meta_sync.py` 的风格）。
- 同一期间重复执行产生新版本，不产生脏数据。

### 5.3 版本与对账

- 提供 `GET /open/v1/orders/versions?period=YYYY-MM` 列出该期间的版本与生成时间（内部对账用，可不对外授权）。
- 每次重算记录：来源批次 ID 列表、命中率、未关联订单数、成本缺失行数。

## 7. 与指标层的衔接

- 明细层是**唯一事实来源**，指标层从明细聚合，不再直接读源批次。

### 2026-10-13 指标引擎的多批次合并（应对上游改版）

指标引擎原先对同一期间只取「最近一次成功批次」，于是 CRM 改版后被 6 字段的残缺批次覆盖，
业务员类指标全部算成 0。现改为：**行内含 `number` 的明细（`orderAnalyze`）按

明细合并成一行。实现见 `backend/app/modules/metric/engine.py` 的 `_load_run_payload`
与 `_set_payload_rows`。

2026-10 因当月只存在改版后的 6 字段批次（无可合并的旧批次），依赖 `create_id` /
`status` / `is_new` 的指标仍为 0，需 CRM 恢复字段后才能恢复。

### 12.6 当前口径限制

1. `入库数量` 取生产订单里「整机」分录的合格入库数（含 `C.` 的半成品分录优先；单分录直接取；
   多分录且入库数一致取该值；否则取最大的一条并打 `inbound_qty_approx` 标记）。2026-09 有 1040 张
   订单关联到生产订单，其中 876 张入库数量与订单数量一致。
2. `订单毛利` = 净出货 − 标准单位成本 × 入库数量；`入库未税` 与「毛利扣减成本」同口径。
   两者都未扣运费/设计费分摊，`total_cost`（整单成本合计）仅作参考。
3. `应收余额`、`逾期天数`、`回款金额` 仍为空（客户维度未打通 / 缺金蝶收款单）。
4. `SKU` 为空（orderAnalyze 无 SKU，需另定代理口径）。

### 12.7 修复记录：客户资料取错字段（2026-10-13）

**现象**：订单全链路里 1245 / 1419 单（87.7%）客户名称不对，显示成旺旺号（如 `tb695515_99`、`宋小玉0205，tb81338125`）。

**原因**：内贸订单的 `customer_name` 字段为空，构建时兜底取了订单上的 `wangwang`。
`wangwang` 是**旺旺号/客户备注**，不是客户名称。

**修复**：客户名称以《客户列表接口》`/hs/customer/getCusotmerList` 为准（按 `customer_id` → `id` 关联），
订单上的 `customer_name` / `customer_name_retail` 只作兜底；`wangwang` 不再参与客户名。

同时补两个字段：`customer_number`（客户编号）、`customer_principal`（客户所属业务员）。

**数据源现状**：客户列表已同步（任务 73，最新批次 24954 行，每周一 02:00）。

**修复结果**：

| 项 | 修复前 | 修复后 |
| --- | --- | --- |
| 客户名与客户列表不一致 | 1245 / 1419 | **0 / 1419** |
| 客户编号有值 | 0 | 1419 / 1419 |
