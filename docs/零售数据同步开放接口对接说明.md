# 零售数据同步开放接口对接说明

> 接口：`POST /open/v1/retail/orders/sync`  
> 用途：外部系统（奇门/聚水潭/中间件）**主动推送**零售订单，本系统幂等落库；可选回放到
> `meta_sync_run`，供现有「零售出库未税总金额」指标取数。  
> 适用场景：本系统不能主动访问上游，只能由上游/中间件把数据推进来。

## 1. 接入前准备

该接口**不校验开放平台令牌**，外部系统直接调用即可，不需要 `app_id/app_secret`。

建议在网关/Nginx 层按来源 IP 做白名单与限流；接口自身限制单次 2000 单、请求体 20MB。

如果希望推送数据参与零售指标计算，执行一次：

```bash
python scripts/seed_retail_push_job.py
```

脚本会创建「零售数据-外部推送」任务；接口按该任务名自动回放，无需再配置应用。

## 2. 鉴权

无。不要发送 `Authorization` 请求头。

## 3. 推送接口

### 3.1 请求

```
POST /open/v1/retail/orders/sync
Content-Type: application/json
X-Request-ID: <建议每次唯一，也可放在 body.request_id>
```

支持四种请求体，任选其一：

```json
// A. 直接提交奇门/聚水潭原始返回（推荐）
{"data_count": 6, "has_next": false, "orders": [ ... ]}

// B. 聚水潭 datas 数组
{"datas": [ ... ]}

// C. data 包裹
{"data": {"orders": [ ... ], "has_next": false, "params": { ... }}}

// D. 裸订单数组
[ { "so_id": "...", "items": [ ... ] } ]
```

推荐在原始返回外加一层控制字段：

```json
{
  "request_id": "qimen-20261023-001",
  "source": "qimen",
  "orders": [ ... ],
  "has_next": false,
  "page_index": 1,
  "page_size": 100,
  "params": {"start_time": "2026-10-23 11:20:00"}
}
```

### 3.2 必填与映射

每单至少要有 `so_id` 或 `o_id`；其余字段缺失不影响入库。

| 上游字段 | 落库位置 | 说明 |
| --- | --- | --- |
| `so_id` / `o_id` | `retail_order.so_id` / `o_id` | 业务唯一键优先用 `so_id`，缺失用 `o_id` |
| `shop_id` | `retail_order.shop_id` | 与 `so_id` 一起构成唯一键；缺失按 `0` |
| `status` | `retail_order.status` | 原样保存，不按状态过滤 |
| `order_date` / `pay_date` / `modified` | 对应时间列 | 用于期间归属与旧版本判断 |
| `paid_amount` / `pay_amount` / `buyer_paid_amount` / `seller_income_amount` | 订单金额列 | 字符串/数字都兼容 |
| `items[]` | `retail_order_item` | 每次更新整单替换明细；`oi_id` 为行唯一键 |
| `items[].qty` / 金额 / `sku_id` / `name` | 明细对应列 | `qty=0`、`Replaced` 行也会保留，便于审计 |

期间 `period_value` 按以下顺序取第一个非空时间归月：

```
io_date → pay_date → order_date → created → modified
```

### 3.3 幂等与更新规则

- **请求级幂等**：`X-Request-ID` 或 `body.request_id` 相同，直接返回首次结果，`duplicate=true`；
  未传时用请求体 SHA256 作为幂等键。
- **订单级更新**：同一 `source + shop_id + so_id/o_id` 执行 upsert；
  明细每次整单替换，避免残留旧行。
- **旧版本保护**：本次 `modified` 早于已入库 `modified` 时跳过，返回 `stale` 计数，不覆盖新数据。
- **内容未变**：订单 JSON 哈希一致时返回 `unchanged`，不写库。
- **单条失败不影响整批**：失败订单写入 `errors`，其余订单正常提交；整批返回 `partial`。

### 3.4 分页

上游 `has_next=true` 时，按页继续推送；每页使用不同的 `request_id`：

```json
{"request_id":"qimen-20261023-p1","orders":[...],"has_next":true,"page_index":1}
{"request_id":"qimen-20261023-p2","orders":[...],"has_next":false,"page_index":2}
```

单次最多 2000 单、请求体建议不超过 20MB。

## 4. 响应

```json
{
  "code": 0,
  "msg": "零售订单同步完成",
  "success": true,
  "status_code": 200,
  "data": {
    "batch_id": "push-20261023112500000000",
    "request_id": "qimen-20261023-001",
    "duplicate": false,
    "received": 6,
    "created": 5,
    "updated": 1,
    "unchanged": 0,
    "stale": 0,
    "failed": 0,
    "item_count": 31,
    "periods": ["2026-10"],
    "has_next": false,
    "errors": [],
    "metric_sync": [
      {"period_value":"2026-10","status":"published","run_id":123,"row_count":6}
    ]
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `created` / `updated` | 新增 / 更新订单数 |
| `unchanged` | 内容哈希未变，未写库 |
| `stale` | 上游修改时间更旧，已跳过 |
| `failed` | 解析或写库失败的单数，明细看 `errors` |
| `item_count` | 本次实际落库的明细行数 |
| `periods` | 涉及期间，指标回放按期间分组 |
| `metric_sync` | 找到「零售数据-外部推送」任务时的回放结果 |

判断成功看 `code == 0` 或 `success == true`，不要只看 HTTP 200。

## 5. 指标联动

现有指标 `retail_outbound_untaxed_amount` 从 `meta_sync_run` 取数。要让推送数据参与计算：

1. 执行 `python scripts/seed_retail_push_job.py`，创建「零售数据-外部推送」任务；
2. 接口会按任务名自动找到它；也可以用环境变量 `RETAIL_SYNC_JOB_ID` 指定其他任务 ID；
3. 推送后接口会为每个期间生成一条 `success` 批次，`rows_json.datas` 为该期间全部已入库订单；
4. 指标配置的 `source_object_code` 要指向该任务的来源对象，`kind=sales_outbound_amount`；
5. 重新计算：

```bash
python scripts/run_metric_calc.py --code retail_outbound_untaxed_amount --period 2026-10
```

如果沿用现有聚水潭任务：设置 `RETAIL_SYNC_JOB_ID=<该任务ID>`，并把它的 Cron 改为不会触发的
表达式（如 `0 0 2 * * ? 2000;0 20 12 * * ? 2000;0 20 18 * * ? 2000`，年份固定 2000），
避免定时主动拉取生成更新的批次、覆盖推送数据。

`RETAIL_SYNC_JOB_ID` 可写在 `backend/env/.env.dev` / `.env.prod`，例如：

```
RETAIL_SYNC_JOB_ID=12
```

**金额口径提示**：如果推送的是订单表（本说明示例），建议指标 `amount_source` 使用
`order.paid_amount` 或 `order.buyer_paid_amount`，不要按明细行求和，避免组合装/换货行重复计数。
如果推送的是已出库单，可继续用 `items.auto`。

## 6. 错误码

| 业务码 | HTTP | 含义 | 处理 |
| --- | --- | --- | --- |
| `0` | 200 | 成功 | — |
| `40104` | 400/413 | 请求体没有订单、超过单次上限或超过 20MB | 检查 `orders/datas/data` 结构并分页/压缩 |

## 7. 常见问题

- **推送成功但指标没变**：确认已创建「零售数据-外部推送」任务（或设置了 `RETAIL_SYNC_JOB_ID`），且指标指向同一来源对象；
  再确认期间是否一致（`periods` 返回的月份）。
- **金额为 0**：上游订单金额字段为空，或指标用了不适用的 `amount_source`；检查入库后的
  `retail_order.pay_amount/buyer_paid_amount` 与指标口径。
- **订单被跳过**：查看响应 `stale`；上游 `modified` 比库里旧时不会覆盖。
- **同一单重复出现**：以 `so_id`（缺失时 `o_id`）为准；不同店铺同号会视为两单。
- **需要补历史**：按月份逐页推送即可，接口不做“只收当月”限制。

## 9. 上线步骤

```bash
cd backend

# 1) 应用迁移（存量库）
python main.py upgrade --env=dev

# 2) 创建「零售数据-外部推送」任务（用于指标回放）
python scripts/seed_retail_push_job.py

# 3) 自检（可选，离线校验迁移可升可降）
python scripts/check_retail_migration.py
```

生产环境把 `--env=dev` 换成 `--env=prod`。

前端构建并发布：

```bash
cd frontend/web
pnpm install
pnpm run build:prod
# 将 dist/* 发布到现有 nginx 站点目录
```

重新登录后台，左侧菜单「开放接口 → 零售订单同步」，可查看订单明细与推送批次。

测试数据：`deploy/retail-push-20261023/test_retail_sync.json`（虚构数据）。

```bash
curl -X POST "http://120.237.174.243:6479/open/v1/retail/orders/sync" \
  -H "Content-Type: application/json" \
  -H "X-Request-ID: retail-test-20261023-001" \

```
